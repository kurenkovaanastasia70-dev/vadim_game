# Покрытие кода тестами и полный набор проверок

Учебная теория на примере Vadim Game.

## 1. Что такое покрытие тестами

Покрытие тестами — это измерение того, какая часть исполняемого кода была выполнена во время тестов.

Покрытие отвечает на вопрос:

> Какие строки или ветви кода уже были затронуты тестами?

Оно не отвечает на вопрос «все ли ошибки найдены». Строка может выполниться, но проверка результата может быть слишком слабой. Поэтому покрытие — это индикатор риска, а не доказательство качества.

## 2. Основные виды покрытия

### Покрытие строк

Показывает долю выполненных строк:

```text
покрытие строк = выполненные строки / все измеряемые строки × 100%
```

Например, 80 выполненных строк из 100 дают 80% покрытия строк.

### Покрытие операторов

Похоже на покрытие строк, но учитывает исполняемые инструкции. Это основная метрика, которую показывает `coverage.py` в таблице `Stmts`.

### Покрытие ветвей

Проверяет не только строку, но и варианты перехода:

```python
if battery > 0:
    use_flashlight()
else:
    show_empty_message()
```

Для хорошего branch coverage тест должен проверить и заряженную батарею, и пустую.

### Покрытие функций

Показывает, какие функции были вызваны. Это полезная быстрая метрика, но она слабее покрытия строк: вызов функции ещё не означает, что проверены все её условия.

## 3. Как читать отчёт coverage.py

Пример:

```text
Name                  Stmts   Miss  Cover   Missing
---------------------------------------------------
inventory_system.py     788    417    47%   40, 46, 57...
TOTAL                  5799   3576    38%
```

- `Stmts` — количество измеряемых инструкций;
- `Miss` — сколько инструкций не выполнялось;
- `Cover` — процент покрытия;
- `Missing` — номера строк, которым не хватило тестов.

В нашем проекте показатель используется как baseline: сначала важно покрыть критические игровые сценарии — запуск, уровни, инвентарь, сохранения, призрака и переходы. Большой файл отрисовки не нужно пытаться закрыть одним огромным GUI-тестом.

## 4. Как запустить покрытие локально

Установка зависимостей:

```bash
python -m pip install -r requirements.txt
```

Запуск всех Python-тестов с измерением покрытия:

```bash
python -m coverage run -m unittest discover -s tests -v
python -m coverage report -m
python -m coverage html -d coverage_html
```

После этого подробный HTML-отчёт находится в `coverage_html/index.html`.

## 5. Что измеряется в нашем проекте

Конфигурация `.coveragerc`:

- измеряет игровые модули;
- не считает сами тесты за production-код;
- не включает учебные скрипты `tools_test_*.py`;
- не включает редактор уровней, потому что это отдельный инструмент;
- исключает только стандартный блок запуска файла `if __name__ == "__main__"`.

## 6. Какие виды тестов есть у нас

| Вид теста | Где находится | Что проверяет |
|---|---|---|
| Unit | `tests/test_lesson_testing_examples.py` | правило получения следующего уровня |
| Integration | там же и `test_game_baseline.py` | сохранение, загрузка, инвентарь и игра вместе |
| Functional / acceptance | там же | победа и переход с уровня 1 на уровень 2 |
| Smoke | там же | запуск игры, загрузка уровня и отрисовка кадров |
| Regression | там же | безопасная обработка повреждённого сохранения |
| GUI / end-to-end | `tools_test_gui.py` | путь игрока через меню, игру, журнал и выход |
| Sanity | `tools_test_sanity.py` | sanity, предметы, задания, достижения и boost-сценарии |
| Static check | GitLab job `compile` | синтаксическая компиляция Python-файлов |

Важно: coverage измеряет Python-тесты `unittest`. GUI smoke и sanity запускаются отдельными jobs, потому что это исполняемые сценарии со своим жизненным циклом Pygame.

## 7. Как тесты запускаются в CI/CD

В `.gitlab-ci.yml` есть только стадия `test`:

1. `unit-and-integration` запускает весь `unittest discover`, считает покрытие, публикует отчёт и проверяет минимум 30%;
2. `sanity` запускает расширенную проверку игровой логики;
3. `compile` проверяет синтаксис всех Python-файлов;
4. `gui-smoke` запускает GUI-сценарий в headless-режиме Pygame.

Если падает любая job, pipeline становится красным. Deployment в этом проекте намеренно отсутствует.

## 8. Почему нельзя гнаться только за процентом

Плохой тест может выполнить строку, но ничего полезного не проверить:

```python
game.use_item(item)  # строка выполнена, результат не проверен
```

Хороший вариант проверяет наблюдаемое поведение:

```python
before = manager.get_count(ItemType.CANDLE)
self.assertTrue(manager.use_item(ItemType.CANDLE))
self.assertEqual(manager.get_count(ItemType.CANDLE), before - 1)
```

Лучше 70% meaningful coverage с проверкой игровых правил, чем 100% покрытия пустыми assertions.

## 9. Как увеличивать покрытие правильно

1. Сначала выбрать важный сценарий и описать ожидаемый результат.
2. Добавить тест на обычный путь.
3. Добавить тесты на ошибки и граничные значения.
4. Проверить обе ветки `if` и варианты состояния предмета.
5. Запустить coverage и посмотреть `Missing`.
6. Не добавлять тест только ради увеличения числа процентов.

## 10. Практическое задание

Для одного предмета инвентаря добавьте:

- успешное использование;
- отказ при нулевом количестве;
- проверку изменения состояния игрока или призрака;
- проверку сохранения и восстановления состояния.

Затем сравните отчёт до и после и объясните, какие строки и ветви стали покрыты.
