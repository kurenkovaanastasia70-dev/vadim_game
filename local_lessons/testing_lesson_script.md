# Сценарий урока: тестирование baseline-версии игры

## Как пользоваться этим документом

Это не просто теория и не список команд. Урок идёт по схеме:

1. объясняем идею на жизненном примере;
2. формулируем правило игры;
3. открываем реальный файл в ветке `stabilize_game_baseline`;
4. разбираем синтаксис по частям;
5. запускаем тест;
6. обсуждаем, какой баг он ловит и какой не ловит;
7. задаём вопрос на понимание.

Все ссылки ниже ведут на реальные файлы baseline-ветки. Если GitLab/GitHub открывает Markdown из корня репозитория, пути работают как относительные ссылки.

Главная цель урока: научиться не «писать проверки ради галочки», а переводить игровое правило в воспроизводимый тест.

## 0. Подготовка урока

### Строгий порядок блока «виды тестов»

После общей теории типы тестов проходим именно в таком порядке — от самого маленького уровня к самому широкому:

1. **Unit** — одна функция или одно правило.
2. **Integration** — несколько модулей вместе.
3. **Functional / acceptance** — законченное требование игрока.
4. **Smoke** — быстрый запуск главного пути.
5. **Regression** — защита от возврата найденного бага.
6. **GUI / E2E** — полный путь пользователя через интерфейс.
7. **Sanity** — расширенная проверка набора игровых правил.

Для каждого типа используем одну и ту же учебную рамку:

```text
теория → жизненный пример → правило игры → реальный файл baseline
→ разбор синтаксиса → запуск → что ловит / что не ловит → вопрос
```

Не переходите к следующему типу, пока ученик не может ответить на два вопроса: «какой слой системы проверяет этот тест?» и «какую ошибку он не обнаружит?»

### Что открываем перед началом

- ветка: `stabilize_game_baseline`;
- игра: `main_work.py`;
- основной набор тестов: [`tests/test_game_baseline.py`](../tests/test_game_baseline.py);
- учебные примеры видов тестов: [`tests/test_lesson_testing_examples.py`](../tests/test_lesson_testing_examples.py);
- sanity-сценарий: [`tools_test_sanity.py`](../tools_test_sanity.py);

- CI-конфигурация: [`.gitlab-ci.yml`](../.gitlab-ci.yml);
- зависимости: [`requirements.txt`](../requirements.txt).

### Команды подготовки

```bash
python --version
python -m pip install -r requirements.txt
python -m unittest discover -s tests -v
```

Что означает последняя команда:

- `python -m` — запустить модуль как программу;
- `unittest` — стандартный тестовый фреймворк Python;
- `discover` — автоматически найти тесты;
- `-s tests` — искать их в папке `tests`;
- `-v` — включить подробный вывод названий тестов.

Если команда завершается `OK`, это означает только, что найденные тесты прошли. Это ещё не означает, что проверена каждая игровая механика.

### Вопрос перед стартом

Если тесты не нашли ни одного тестового файла, команда может завершиться без ошибок. Почему одного зелёного результата команды недостаточно? Что нужно проверить в выводе?

Ожидаемая мысль: нужно увидеть количество реально запущенных тестов, например `Ran 14 tests`.

## 1. Baseline: какую версию мы считаем стабильной

### Теория

`Baseline` — это зафиксированная точка, от которой команда продолжает разработку. Это не «идеальная игра» и не «все идеи уже реализованы».

У baseline должны быть:

- понятная граница возможностей;
- рабочий главный игровой сценарий;
- известные ограничения;
- автоматические проверки критических правил;
- повторяемая установка и запуск.

### Жизненный пример

Представим школьный проект. Ученик говорит: «Инвентарь работает». Но что это значит?

Это может означать разные вещи:

- предмет отображается в списке;
- предмет можно выбрать;
- предмет уменьшается после использования;
- предмет не используется при нулевом количестве;
- размещаемый предмет появляется на карте;
- состояние предмета сохраняется между загрузками.

Пока команда не выбрала точное значение, невозможно написать хороший тест.

### Практика на нашей игре

В baseline проверяются загрузка уровней, игровой цикл, предметы, проектор, сохранения, призрак и переход между уровнями. Начать можно с тестов:

- [`test_level_catalog_is_complete_and_loads`](../tests/test_game_baseline.py#L36);
- [`test_headless_gameplay_frames_are_stable`](../tests/test_game_baseline.py#L52);
- [`test_inventory_items_have_safe_use_paths`](../tests/test_game_baseline.py#L60);
- [`test_projector_can_be_placed_and_powered`](../tests/test_game_baseline.py#L100);
- [`test_level_transition_keeps_campaign_consistent`](../tests/test_game_baseline.py#L167).

### Как объяснить ученику

Каждый тест — это маленькое утверждение о baseline:

```text
уровень можно загрузить;
игра переживает несколько кадров;
предмет можно безопасно использовать;
проектор можно разместить и запитать;
победа переводит на следующий уровень.
```

### Вопрос на понимание

Игра запускается, но после победы игрок всегда остаётся на первом уровне. Что это: косметический дефект или нарушение baseline? Какое правило нужно сформулировать перед написанием теста?

## 2. Что такое тест: Arrange — Act — Assert

### Теория

Хороший тест обычно состоит из трёх частей:

1. **Arrange** — подготовить начальное состояние.
2. **Act** — выполнить действие.
3. **Assert** — проверить ожидаемый результат.

Без третьей части это часто не тест, а просто запуск кода.

### Жизненный пример вне игры

Проверяем кнопку лифта:

- Arrange: лифт стоит на первом этаже;
- Act: нажимаем кнопку третьего этажа;
- Assert: лифт приехал на третий этаж.

Факт «мы нажали кнопку» ещё не доказывает, что лифт приехал.

### Пример на нашей игре

Учебный functional-тест находится в [`test_functional_level_transition`](../tests/test_lesson_testing_examples.py#L61):

```python
game = self.new_game()                 # Arrange
game.current_level_id = "level_1"
game.player_level = 1
game.win_next_level_id = "level_2"

result = game.advance_to_next_level()  # Act

self.assertTrue(result)                # Assert
self.assertEqual(game.current_level_id, "level_2")
self.assertEqual(game.player_level, 2)
```

### Разбор синтаксиса

- `game = self.new_game()` — присваиваем переменной объект игры;
- `=` — оператор присваивания;
- `"level_1"` — строковое значение;
- `game.current_level_id` — обращение к атрибуту объекта;
- `game.advance_to_next_level()` — вызов метода;
- `result` — сохраняем возвращаемое значение;
- `self.assertTrue(result)` — проверяем, что результат логически истинный;
- `self.assertEqual(actual, expected)` — сравниваем фактическое и ожидаемое значения.

В `unittest` assertion при несоответствии выбрасывает ошибку, и тест становится красным.

### Вопрос на понимание

В тесте есть вызов `game.advance_to_next_level()`, но нет ни одного `assert`. При каких изменениях игры такой тест может остаться зелёным, хотя переход перестал работать?

## 3. Библиотека `unittest`: минимальный синтаксис

### 3.1. Тестовый класс

В начале учебного файла импортируется стандартная библиотека:

```python
import unittest
```

Класс тестов наследуется от `unittest.TestCase`:

```python
class LessonTestingExamples(unittest.TestCase):
    ...
```

Наследование даёт классу готовые методы `assertEqual`, `assertTrue`, `assertIsNone`, `assertGreater` и другие.

Реальный код: [`LessonTestingExamples`](../tests/test_lesson_testing_examples.py#L24).

### 3.2. Имена тестов

Метод должен начинаться с `test_`:

```python
def test_unit_level_catalog_rule(self):
    ...
```

Именно по этому префиксу `unittest discover` понимает, какие методы запускать.

Если назвать метод `check_level_catalog`, тест обычно не будет найден автоматически.

### 3.3. Часто используемые assertions

```python
self.assertEqual(actual, expected)       # равенство
self.assertNotEqual(actual, unexpected)  # неравенство
self.assertTrue(condition)               # условие истинно
self.assertFalse(condition)              # условие ложно
self.assertIsNone(value)                 # значение None
self.assertIsNotNone(value)              # значение не None
self.assertGreater(value, minimum)       # больше
```

Порядок аргументов важен: сначала обычно пишем фактическое значение, затем ожидаемое. Если тест упадёт, сообщение будет понятнее.

### 3.4. Подготовка и очистка

В учебных тестах есть `setUpClass` и `tearDownClass`:

```python
@classmethod
def setUpClass(cls):
    pygame.init()
    pygame.display.set_mode((1, 1))

@classmethod
def tearDownClass(cls):
    pygame.quit()
```

- `@classmethod` означает, что метод работает с классом, а не с отдельным объектом теста;
- `setUpClass` вызывается один раз перед тестами класса;
- `tearDownClass` вызывается после тестов;
- `pygame.display.set_mode((1, 1))` создаёт маленькое headless-окно для тестового окружения.

Реальный код: [`setUpClass` и `tearDownClass`](../tests/test_lesson_testing_examples.py#L26).

### Вопрос на понимание

Почему `pygame.quit()` в одном тестовом классе может сломать следующий класс тестов? Как помогает собственный `setUpClass`?

## Блок 1. Unit-тест: проверяем одно правило

### Теория

Unit-тест отвечает на узкий вопрос: «Правильно ли работает эта функция или метод в конкретном случае?»

Он должен быть:

- быстрым;
- понятным;
- максимально независимым от окна, файлов и случайности;
- простым для диагностики.

### Жизненный пример

В интернет-магазине есть функция расчёта скидки. Unit-тест проверяет только расчёт скидки, а не оплату, доставку и отправку письма.

### Практика: каталог уровней

```python
def test_unit_level_catalog_rule(self):
    self.assertEqual(get_next_level_id("level_1"), "level_2")
    self.assertIsNone(get_next_level_id("level_2"))
```

Полный пример: [`test_unit_level_catalog_rule`](../tests/test_lesson_testing_examples.py#L40).

Что он проверяет:

- после `level_1` есть `level_2`;
- после последнего уровня нет следующего уровня.

Что он не проверяет:

- кнопку победы;
- загрузку JSON уровня;
- изменение состояния `Game`;
- отрисовку экрана.

### Разбор синтаксиса

`get_next_level_id("level_1")` — вызов функции с одним аргументом.

`self.assertEqual(..., "level_2")` — ожидаем строку `level_2`.

`self.assertIsNone(...)` — специально проверяем отсутствие значения, а не пустую строку и не `False`.

### Жизненный баг

Разработчик добавил `level_3`, но забыл обновить индекс уровней. Unit-тест на каталог сразу покажет ошибку в правиле переходов, ещё до запуска всей игры.

### Вопрос на понимание

Нужно проверить, что кнопка на экране победы действительно вызывает переход. Достаточно ли unit-теста `get_next_level_id`? Если нет, какой следующий уровень теста нужен?

## Блок 2. Integration-тест: проверяем связь компонентов

### Теория

Integration-тест проверяет несколько частей программы вместе. Он нужен там, где каждый компонент по отдельности работает, но договор между ними может быть нарушен.

### Жизненный пример

Форма регистрации отдельно правильно проверяет пароль, а база отдельно умеет сохранять пользователя. Integration-тест проверяет, что форма передаёт базе правильные данные.

### Практика: сохранение и загрузка

Реальный пример: [`test_integration_save_and_load`](../tests/test_lesson_testing_examples.py#L45).

Ключевая часть:

```python
with tempfile.TemporaryDirectory() as temp_dir:
    save_path = os.path.join(temp_dir, "save.json")
    game = self.new_game()
    game.save_file = save_path
    game.player_money = 77
    game.save_game(1)

    restored = self.new_game()
    restored.save_file = save_path
    restored.saves = restored.load_saves()

    self.assertTrue(restored.load_game(1))
    self.assertEqual(restored.player_money, 77)
```

### Разбор синтаксиса

- `with ... as temp_dir` — контекстный менеджер; после блока временная папка удалится;
- `tempfile.TemporaryDirectory()` — создаёт изолированную временную папку;
- `os.path.join(...)` — собирает путь независимо от операционной системы;
- `game.save_file = save_path` — направляет сохранение во временный файл;
- `game.save_game(1)` — сохраняет в слот 1;
- `restored = self.new_game()` — создаёт новую игру, чтобы проверить именно восстановление;
- `self.assertEqual(restored.player_money, 77)` — проверяет, что значение прошло через файл и обратно.

### Связь с production-кодом

Сами методы сохранения находятся в [`main_work.py`](../main_work.py#L1382):

- `load_saves` читает слоты;
- `save_game` записывает состояние;
- тест проверяет их совместную работу, а не внутренние строки реализации.

### Вопрос на понимание

Если тест проверяет только `json.dump`, но не создаёт новый объект `Game` и не вызывает `load_game`, какую важную ошибку он может пропустить?

## Блок 3. Functional / acceptance-тест: проверяем требование игрока

### Теория

Functional-тест проверяет завершённую функцию игры с точки зрения требования. Его не интересует, какой именно внутренний метод использован, если итоговое поведение верное.

Acceptance-тест можно сформулировать как условие приёмки:

> После победы на первом уровне игрок попадает на второй уровень, его уровень кампании увеличивается, а игра возвращается в состояние GAME.

### Практика

Реальный тест: [`test_functional_level_transition`](../tests/test_lesson_testing_examples.py#L61).

```python
game.current_level_id = "level_1"
game.player_level = 1
game.win_next_level_id = "level_2"

self.assertTrue(game.advance_to_next_level())
self.assertEqual(game.current_level_id, "level_2")
self.assertEqual(game.player_level, 2)
self.assertEqual(game.state, GameState.GAME)
```

### Чем он отличается от unit-теста

Unit-тест проверяет функцию каталога уровней.

Functional-тест проверяет уже сценарий кампании: состояние игры, уровень игрока и переход.

Один unit-тест может быть зелёным, а functional-тест красным, если функция каталога правильная, но `Game` неправильно обновляет состояние.

### Жизненный баг

Переход изменяет `current_level_id`, но забывает изменить `player_level`. Экран открывается, однако награды и сложность остаются от первого уровня. Unit-тест может не заметить это, functional-тест заметит.

### Вопрос на понимание

Какое assertion нужно добавить, если бизнес-правило говорит, что после перехода сохранённые предметы должны остаться у игрока?

## Блок 4. Smoke-тест: проверяем запуск главного пути

### Теория

Smoke-тест — короткая проверка «приложение вообще живо?».

Он не пытается проверить каждую кнопку и каждый предмет. Его задача — быстро обнаружить критическую поломку сборки.

### Практика

Реальный пример: [`test_smoke_level_can_start_and_render`](../tests/test_lesson_testing_examples.py#L73).

```python
game = self.new_game()
game.load_level_by_id("level_1")

for _ in range(3):
    game.draw()

self.assertGreater(len(game.walls), 0)
self.assertGreater(len(game.ghost_manager.ghosts), 0)
self.assertIsNotNone(game.player_rect)
```

### Разбор синтаксиса

- `for _ in range(3)` — повторить действие три раза;
- `_` — имя для значения, которое нам не нужно использовать;
- `len(...)` — получить количество элементов;
- `assertGreater(..., 0)` — убедиться, что коллекция не пустая;
- `assertIsNotNone(...)` — проверить наличие объекта игрока.

### Что smoke-тест ловит

- сломанную загрузку уровня;
- отсутствие стен или призраков;
- падение игрового цикла при отрисовке;
- отсутствие позиции игрока.

### Что он не ловит

- неправильную цену предмета;
- ошибку конкретной кнопки;
- неправильную формулу sanity;
- потерю инвентаря при переходе.

### Вопрос на понимание

Почему нельзя заменить весь набор тестов одним smoke-тестом, даже если он проходит 100 кадров без ошибки?

## Блок 5. Regression-тест: не дать багу вернуться

### Теория

Regression-тест появляется из реального дефекта:

1. баг воспроизводится;
2. фиксируется ожидаемое безопасное поведение;
3. пишется тест, который сначала падает;
4. исправляется production-код;
5. тест остаётся навсегда.

### Практика: повреждённое сохранение

Реальный пример: [`test_regression_corrupt_save_is_safe`](../tests/test_lesson_testing_examples.py#L85).

```python
with open(save_path, "w", encoding="utf-8") as save_file:
    save_file.write("{not valid json")

game = self.new_game()
game.save_file = save_path

self.assertEqual(
    game.load_saves(),
    {"slot1": None, "slot2": None, "slot3": None},
)
```

### Разбор синтаксиса

- `open(..., "w", encoding="utf-8")` — открыть файл на запись;
- `with open(...) as save_file` — файл будет закрыт автоматически;
- `write(...)` — записать строку;
- строка `{not valid json` намеренно повреждена;
- assertion проверяет fallback: игра не падает, а возвращает пустые слоты.

### Связь с baseline

Обычный ручной сценарий проверяет правильный save. Regression-тест проверяет плохой вход, который реально может появиться после сбоя записи, ручного редактирования или старой версии игры.

### Вопрос на понимание

Почему тест «файл существует» недостаточен для save-системы? Какие ещё состояния файла нужно проверить?

## Блок 6. GUI/E2E-тест: проверяем путь пользователя

### Теория

End-to-end-тест проверяет систему от начала до конца. GUI-тест работает не с отдельными методами, а с событиями пользователя: кликами и клавишами.

Он дороже и медленнее unit-теста, зато ловит ошибки связки:

- кнопка нарисована не там, где обработчик ожидает клик;
- экран сменился, но состояние не обновилось;
- обработчик клавиши не закрывает журнал;
- диалог выхода не возвращает в меню.

### Практика

Сценарий находится в [`tools_test_gui.py`](../tools_test_gui.py):

1. рисуется меню;
2. выбирается новый слот;
3. выбирается сложность;
4. пропускается boost;
5. загружается игра;
6. отправляется движение;
7. открывается и закрывается журнал;
8. открывается диалог выхода;
9. выполняется возврат в меню.

Например, клик моделируется функцией `click`, которая создаёт событие Pygame:

```python
pygame.event.post(
    pygame.event.Event(
        pygame.MOUSEBUTTONDOWN,
        {"pos": position, "button": 1},
    )
)
handle_event(game)
```

### Разбор синтаксиса

- `pygame.event.Event(...)` — объект события;
- `pygame.MOUSEBUTTONDOWN` — тип события нажатия мыши;
- словарь `{"pos": ..., "button": 1}` — данные события;
- `pygame.event.post(...)` — положить событие в очередь;
- `handle_event(game)` — передать событие игровому обработчику.

### Headless-режим

В CI нет физического монитора. Поэтому в `.gitlab-ci.yml` заданы переменные:

```yaml
SDL_VIDEODRIVER: "dummy"
SDL_AUDIODRIVER: "dummy"
```

Они позволяют Pygame создать тестовое окно без показа пользователю.

### Вопрос на понимание

Если все методы перехода между состояниями покрыты unit-тестами, почему всё равно нужен GUI-тест меню?

## Блок 7. Sanity-тест: расширенный сценарий игровых правил

### Теория

Sanity-тест — это не один универсальный стандарт, а быстрый набор проверок, который отвечает: «основные изменения этой области игры выглядят разумно?»

В нашем проекте отдельный скрипт проверяет больше, чем короткий smoke:

- sanity игрока;
- темноту и свечу;
- возможность охоты призрака;
- предметы;
- задания и деньги;
- достижения;
- boost и переходы.

Файл: [`tools_test_sanity.py`](../tools_test_sanity.py).

Запуск:

```bash
python tools_test_sanity.py
```

В конце скрипт печатает `sanity tests OK`. В отличие от `unittest`, этот файл использует обычные `assert` и возвращает код завершения процесса.

### Разбор `assert`

```python
assert game.player_sanity == 100.0
assert game.is_setup_phase()
```

Если условие ложно, Python выбрасывает `AssertionError`, а CI считает job неуспешной.

Для приблизительных чисел используется собственная функция `approx`, потому что вычисления с `float` могут дать `49.999999` вместо `50.0`.

### Вопрос на понимание

Почему sanity-скрипт может быть удобнее для длинного сценария, а `unittest` — для набора маленьких независимых тестов?

## 11. Покрытие тестами

### Теория

Покрытие отвечает на вопрос: какие инструкции игрового кода выполнялись во время запуска тестов?

Формула:

```text
покрытие = выполненные инструкции / все измеряемые инструкции × 100%
```

Покрытие не отвечает на вопрос «правильно ли написаны assertions». Можно выполнить строку и ничего не проверить.

### Команды

```bash
python -m coverage run -m unittest discover -s tests -v
python -m coverage report -m
python -m coverage html -d coverage_html
```

Синтаксис читается справа налево:

- `coverage run` запускает измерение;
- `-m unittest` говорит coverage запустить модуль unittest;
- `discover -s tests` находит весь набор тестов;
- `coverage report -m` печатает таблицу и строки `Missing`;
- `coverage html -d coverage_html` создаёт подробный браузерный отчёт.

### Как читать таблицу

```text
Name                  Stmts   Miss  Cover   Missing
inventory_system.py     788    416    47%   40, 46, 57...
TOTAL                  5200   2954    43%
```

- `Stmts` — измеряемые инструкции;
- `Miss` — пропущенные инструкции;
- `Cover` — процент;
- `Missing` — строки для поиска новых сценариев.

Настройки исключений находятся в [`.coveragerc`](../.coveragerc). Тесты и учебные скрипты не должны считаться production-кодом.

### Жизненный пример

В коде предмета есть ветка:

```python
if count > 0:
    use_item()
else:
    refuse_use()
```

Если тесты используют предмет только при `count == 1`, строка `refuse_use()` может остаться непокрытой. Нужно добавить сценарий нулевого количества.

### Вопрос на понимание

Почему процент покрытия может вырасти после теста, который только вызывает функцию и ничего не проверяет, но качество игры при этом не вырастет?

## 12. CI без CD

### Теория

**CI — Continuous Integration**: сервер автоматически проверяет изменения после `push` или merge request.

**CD — Continuous Delivery/Deployment**: сервер доставляет или разворачивает подготовленную версию.

В baseline нужен только CI. Мы хотим автоматически проверять код, но пока не публикуем игру на сервер и не делаем deploy.

### Разбор `.gitlab-ci.yml`

Реальная конфигурация: [`.gitlab-ci.yml`](../.gitlab-ci.yml).

```yaml
image: python:3.11

stages:
  - test
```

- `image` — Docker-образ окружения;
- `stages` — порядок крупных этапов pipeline;
- здесь только `test`, поэтому deploy физически не описан.

Переменные Pygame:

```yaml
variables:
  SDL_VIDEODRIVER: "dummy"
  SDL_AUDIODRIVER: "dummy"
```

Общая установка:

```yaml
before_script:
  - python --version
  - python -m pip install --upgrade pip
  - python -m pip install -r requirements.txt
```

`before_script` выполняется перед каждой job.

### Job с unit/integration и coverage

```yaml
unit-and-integration:
  stage: test
  script:
    - python -m coverage run -m unittest discover -s tests -v
    - python -m coverage report -m --fail-under=30
```

- имя до двоеточия — имя job;
- `stage: test` помещает её в тестовый этап;
- `script` — список команд;
- `--fail-under=30` делает job красной, если покрытие упало ниже baseline-порога.

### Остальные job

В конфигурации есть отдельные проверки:

- `sanity` запускает [`tools_test_sanity.py`](../tools_test_sanity.py);
- `compile` запускает `python -m compileall -q .`;
- `gui-smoke` запускает [`tools_test_gui.py`](../tools_test_gui.py).

Все они относятся к `stage: test`. Если одна job падает, pipeline считается неуспешным.

### Жизненный пример

Разработчик изменил обработчик выхода из игры:

- unit-тесты игровой логики зелёные;
- sanity зелёный;
- GUI smoke падает, потому что кнопка теперь открывает не тот экран.

CI не «угадывает», какая реализация красивее. Он показывает, что один из зафиксированных сценариев перестал выполняться.

### Вопрос на понимание

Почему GUI smoke и unit-тесты должны быть отдельными job, а не одним огромным тестовым файлом?

## 13. Практическое задание на уроке

Выберите механику предмета, например свечу, соль или проектор.

### Шаг 1. Запишите правило

Пример:

```text
Если у игрока есть свеча и он использует её,
количество свечей уменьшается на 1,
а в игре появляется зажжённый источник света.
```

### Шаг 2. Определите уровни проверки

- unit: отдельное правило количества;
- integration: инвентарь меняет состояние `Game`;
- functional: игрок использует предмет в сценарии уровня;
- regression: найденный ранее отказ не возвращается;
- GUI: предмет можно выбрать через интерфейс, если это входит в экранный сценарий.

### Шаг 3. Напишите тест

Используйте `Arrange → Act → Assert` и минимум два assertions: результат операции и изменение состояния.

### Шаг 4. Запустите проверки

```bash
python -m unittest discover -s tests -v
python tools_test_sanity.py
python -m coverage run -m unittest discover -s tests -v
python -m coverage report -m
```

### Шаг 5. Обсудите границы

Ответьте:

- что именно тест гарантирует;
- какой случай он не проверяет;
- нужен ли GUI-тест;
- какой новый regression-тест появится после найденного бага.

## 15. Финальные выводы

- Baseline — это контракт минимально стабильной игры.
- Автотест — исполняемое описание ожидаемого поведения.
- Unit-тесты локализуют маленькие правила.
- Integration-тесты проверяют границы модулей.
- Functional-тесты проверяют требования игрока.
- Smoke-тесты быстро проверяют запуск.
- Regression-тесты не дают исправленным багам вернуться.
- GUI/E2E-тесты проверяют путь пользователя через интерфейс.
- Coverage показывает пробелы в выполнении кода, но не заменяет качество assertions.
- CI повторяет проверки на сервере.
- CD сейчас не нужен: baseline проверяем, но не разворачиваем автоматически.
