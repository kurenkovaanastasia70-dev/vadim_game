# Виды тестов в Python и CI/CD

Учебная презентация на примере игры Vadim Game.

---

## Слайд 1. Зачем нужны автотесты

Автотест — это программа, которая сама проверяет ожидаемое поведение другой программы.

Автотесты помогают:

- быстро находить регрессии после изменений;
- проверять правила игры без ручного повторения одних и тех же действий;
- безопаснее разделять проект на ветки;
- документировать ожидаемое поведение кода;
- запускать проверку перед merge в GitLab.

Тест не доказывает, что в программе нет вообще всех ошибок. Он доказывает, что проверенные сценарии сейчас работают.

---

## Слайд 2. Библиотеки и инструменты

В проекте используются:

| Инструмент | Зачем он нужен |
|---|---|
| `unittest` | стандартный фреймворк Python для тестовых классов, assertions и запуска набора тестов |
| `tempfile` | создание временных папок и файлов для теста сохранений без изменения настоящего `save.json` |
| `pygame` | проверка игрового цикла, уровней и предметов; в CI работает с dummy-видеодрайвером |
| `compileall` | проверка, что Python-файлы синтаксически компилируются |
| GitLab CI/CD | автоматический запуск проверок на каждый push или merge request |

Дополнительный `pytest` сейчас не нужен: для учебного примера достаточно встроенного `unittest`. Позже его можно подключить для более короткого синтаксиса, fixtures и отчётов.

## Слайд 3. Общая схема хорошего теста

Почти любой тест строится по схеме **Arrange — Act — Assert**:

1. **Arrange** — подготовить объект и начальное состояние.
2. **Act** — выполнить действие.
3. **Assert** — проверить результат.

```python
game = Game()                         # Arrange
game.current_level_id = "level_1"
game.win_next_level_id = "level_2"

result = game.advance_to_next_level() # Act

assert result is True                  # Assert
assert game.current_level_id == "level_2"
```

## Слайд 4. Unit-тесты

Unit-тест проверяет одну небольшую функцию или метод изолированно.

Пример из `tests/test_lesson_testing_examples.py`:

```python
def test_level_catalog_returns_next_level(self):
    self.assertEqual(get_next_level_id("level_1"), "level_2")
    self.assertIsNone(get_next_level_id("level_2"))
```

Здесь проверяется только правило каталога уровней. Такой тест быстрый и точно показывает, где возникла ошибка.

---

## Слайд 5. Integration-тесты

Интеграционный тест проверяет взаимодействие нескольких частей программы.

Пример: игра сохраняет состояние, а новый объект игры загружает его обратно.

```python
game.save_game(1)
restored = Game()
restored.save_file = save_path
restored.saves = restored.load_saves()

self.assertTrue(restored.load_game(1))
self.assertEqual(restored.player_money, 77)
```

Здесь вместе работают `Game`, JSON-сохранение, `InventoryManager` и загрузка уровня.

---

## Слайд 6. Functional / acceptance-тесты

Функциональный тест проверяет пользовательский сценарий целиком: что должно произойти с точки зрения игрока.

Пример сценария:

```python
game.current_level_id = "level_1"
game.win_next_level_id = "level_2"

self.assertTrue(game.advance_to_next_level())
self.assertEqual(game.current_level_id, "level_2")
self.assertEqual(game.state, GameState.GAME)
```

Это проверка требования: после победы игрок переходит на следующий уровень и игра снова находится в игровом состоянии.

---

## Слайд 7. Smoke-тесты

Smoke-тест — короткая проверка, что приложение вообще запускается и главный сценарий не сломан.

В проекте smoke-проверка:

- создаёт игру;
- загружает уровень;
- убеждается, что есть стены, игрок и призрак;
- отрисовывает несколько кадров.

```python
game = Game()
game.set_state(GameState.GAME)
game.load_level_by_id("level_1")

for _ in range(30):
    game.draw()

self.assertGreater(len(game.ghost_manager.ghosts), 0)
```

## Слайд 8. Regression-тесты

Регрессионный тест закрепляет баг, который уже был найден и исправлен.

Пример для игры: повреждённый файл сохранения не должен падать с исключением и должен превращаться в пустые слоты.

```python
with open(save_path, "w", encoding="utf-8") as file:
    file.write("{not valid json")

self.assertEqual(
    game.load_saves(),
    {"slot1": None, "slot2": None, "slot3": None},
)
```

Если такой баг вернётся, CI сразу сообщит об этом.

## Слайд 9. GUI / end-to-end smoke-тест

GUI-тест работает с настоящим окном и событиями Pygame.

`tools_test_gui.py` проверяет цепочку:

`меню → сохранения → сложность → boost → игра → движение → журнал → выход`

Он отправляет мышиные и клавиатурные события, делает скриншоты и проверяет переходы между экранами.

В GitLab используется `SDL_VIDEODRIVER=dummy`, поэтому тест можно запустить без физического монитора. Это всё ещё проверка Pygame-окна, но без показа окна пользователю.

## Слайд 10. Разница между видами тестов

| Вид | Что проверяет | Скорость | Пример |
|---|---|---:|---|
| Unit | одну функцию/метод | очень быстро | следующий уровень |
| Integration | связи модулей | быстро | сохранение + загрузка |
| Functional | пользовательский сценарий | средне | победа и переход |
| Smoke | приложение запускается | быстро | загрузка уровня и кадры |
| Regression | исправленный баг не вернулся | зависит от сценария | повреждённый save |
| GUI/E2E | путь пользователя через интерфейс | медленнее | меню → игра → журнал |

Лучше иметь много быстрых unit-тестов, меньше integration-тестов и несколько важных GUI-сценариев.

## Слайд 11. Что такое CI/CD

**CI — Continuous Integration, непрерывная интеграция.**

После push или создания merge request сервер автоматически собирает окружение и запускает тесты. Ошибка не позволяет считать изменение готовым.

**CD — Continuous Delivery/Deployment, непрерывная доставка/развёртывание.**

После успешных проверок система может подготовить релиз или отправить приложение на сервер.

В нашем учебном проекте настраивается только CI: автоматические тесты. Deployment не выполняется, потому что игру пока не нужно автоматически публиковать.

## Слайд 12. Как работает GitLab CI в этом проекте

Файл `.gitlab-ci.yml` описывает pipeline с одной стадией `test`.

В pipeline запускаются отдельные jobs:

1. `unit-and-integration` — тесты из `tests`;
2. `sanity` — расширенная проверка игровых правил;
3. `compile` — проверка синтаксиса Python;
4. `gui-smoke` — headless-проверка интерфейсного сценария.

Если хотя бы одна job завершается с ошибкой, pipeline красный. Это сигнал, что ветку нужно исправить до merge.

---

## Слайд 13. Команды локального запуска

```bash
python -m unittest discover -s tests -v
python tools_test_sanity.py
python -m compileall -q .
python tools_test_gui.py
```

Перед push полезно запустить тот же набор, который запустит GitLab.

---

## Слайд 14. Что считается хорошим тестом

- Тест проверяет одну понятную причину.
- Название описывает ожидаемое поведение.
- Тест не зависит от порядка запуска других тестов.
- Временные файлы удаляются автоматически.
- Проверяется результат, а не внутренние детали без необходимости.
- Тест можно повторить локально той же командой, что и в CI.

## Слайд 15. Практическое задание

1. Найдите в игре один предмет и сформулируйте его ожидаемое поведение.
2. Напишите unit-тест для отдельного правила.
3. Напишите integration-тест для связи инвентаря и игры.
4. Добавьте regression-тест для найденного бага.
5. Сделайте push и откройте pipeline в GitLab.
6. Если pipeline красный, прочитайте лог первой упавшей job и исправьте причину.

Главная идея: тест — это исполняемое описание того, как должна работать игра.
