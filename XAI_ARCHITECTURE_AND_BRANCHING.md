# Архитектура двух проектов и стратегия разделения репозитория

Документ описывает, как из текущего проекта сделать два связанных, но независимых результата:

1. **Игру** — стабильный пользовательский продукт с игровыми механиками, уровнями, инвентарём и прогрессом.
2. **Школьный проект** — исследовательский форк игры для изучения способов объяснения решений игрового ИИ.

Исходная идея школьного проекта находится в [xai_game_project_idea.md](xai_game_project_idea.md). Этот документ дополняет её техническим планом, привязанным к фактической структуре текущего репозитория.

## 1. Текущее состояние исходного проекта

На момент подготовки документа активна ветка `main`. Основные части приложения:

| Компонент | Текущее расположение | Ответственность |
|---|---|---|
| Точка входа и игровой цикл | `main_work.py` | Класс `Game`, состояния приложения, уровни, камера, сохранения, обновление игровых систем |
| Обработка ввода | `handlers.py` | Обработка событий Pygame для меню, игры, магазина, настроек и других экранов |
| Отрисовка | `draws.py` | Игровой мир, HUD, меню, призрак, эффекты видимости |
| Движение и карта | `mechanics.py` | Перемещение игрока, коллизии, загрузка и масштабирование JSON-уровней |
| ИИ противника | `ghost.py` | FSM призрака, восприятие игровых условий, A*, движение, способности и взаимодействия |
| Предметы | `inventory_system.py` | Инвентарь, расходники, размещаемые предметы, проектор и его зоны |
| Конфигурация | `ghost_abilities.ini`, `level*.json` | Параметры способностей, уровни, комнаты, стены и точки появления |
| Ассеты | `assets/`, `sprite_parts/` | Изображения и кадры анимации |
| Документация | `ARCHITECTURE.md`, `DEVELOPMENT_PLAN.md` | Описание текущей реализации и планы развития |

В текущей игре ИИ призрака реализован как конечный автомат с A* и правилами переходов. Это будет **игровым baseline**, но не итоговым ИИ школьного проекта. В школьной ветке необходимо добавить ML-модель, которая получает признаки игровой ситуации и сама предсказывает действие призрака. FSM останется учителем для генерации разметки и контрольным ориентиром, а предметом исследования станет объяснение решений именно ML-модели.

Текущие состояния призрака:

```text
INVISIBLE -> IDLE -> PATROL <-> WANDER
                    |       |
                    +-----> CHASE -> SEARCH -> PATROL
                                      |
                                      +-------> RETURN -> PATROL
```

Фактические переходы нужно проверять по условиям в `Ghost.update_state()`; схема выше показывает логическую роль состояний, а не гарантирует единственный путь перехода.

## 2. Главный принцип разделения

Разделение нужно делать не в начале разработки и не через копирование текущей папки в случайный момент. Сначала необходимо зафиксировать рабочую версию игры, а затем создать школьный проект от конкретного стабильного коммита.

Рекомендуемая схема:

```text
                    tag: game-v1.0-baseline
                   /
game repository --- main ---------------------> развитие игры
                   \
                    school-xai ----------------> исследовательский форк
                         |
                         +-- xai/telemetry
                         +-- xai/explanations
                         +-- experiments
```

После точки разделения изменения школьного проекта не должны автоматически попадать в игровую ветку. Общие исправления можно переносить вручную или через выборочное применение коммитов, но только если они не меняют экспериментальные условия.

## 3. Когда форкнуться

### До форка: обязательная стабилизация игры

Форк создаётся после выполнения следующих условий:

- игра запускается из чистого клона командой `python main_work.py`;
- редактор уровней запускается командой `python level_editor.py` либо явно зафиксировано, что он не входит в школьный эксперимент;
- выбран один стабильный уровень и одна конфигурация сложности;
- проверены основные сценарии: старт уровня, движение, видимость, появление призрака, преследование, улики, столкновение, победа и проигрыш;
- `save.json` и другие локальные файлы сохранения не включаются в коммит;
- найден и зафиксирован текущий код решений призрака в `ghost.py`;
- создан минимальный тестовый чек-лист или sanity-тест для повторной проверки baseline;
- в репозитории нет незапланированных незакоммиченных изменений.

Перед форком полезно сделать отдельный коммит только с документацией идеи и архитектуры. Это позволяет однозначно ответить, от какой версии игры началось исследование.

### Точка форка

Пример команд в исходном репозитории:

```bash
git switch main
git pull --ff-only
python main_work.py
git add xai_game_project_idea.md XAI_ARCHITECTURE_AND_BRANCHING.md
git commit -m "docs: define game and school project split"
git tag -a game-v1.0-baseline -m "Stable baseline for the game and XAI project"
git push origin main --tags
git switch -c school-xai
git push -u origin school-xai
```

Если школьный проект должен быть отдельным публичным репозиторием, после создания ветки следует создать отдельный репозиторий и отправить туда ветку `school-xai`. Исходный игровой репозиторий при этом остаётся самостоятельным.

## 4. Что остаётся в проекте игры

В игровом проекте сохраняются и развиваются пользовательские функции:

- игровой цикл и управление игроком;
- карта, комнаты, стены и коллизии;
- призрак, его способности, FSM и A*;
- предметы, инвентарь, улики и проектор;
- уровни, магазин, сохранения, достижения и прогресс;
- меню, HUD, эффекты видимости, звук и визуальный стиль;
- редактор уровней;
- производительность, исправления ошибок и совместимость запуска.

В игровой ветке не следует добавлять исследовательские панели, отладочные поля зрения, экспериментальные анкеты и обязательную запись каждого решения ИИ. Такие функции могут ухудшить игровой опыт и изменить поведение, которое должно оставаться продуктовым.

### Ветки игрового проекта

```text
main
 ├── feature/<новая игровая функция>
 ├── fix/<исправление>
 └── release/<подготовка версии>   # при необходимости
```

Рабочий порядок для игры:

1. Разработка ведётся в отдельной feature/fix-ветке.
2. Проверяется запуск и затронутый сценарий.
3. Изменение вливается в `main` небольшим самостоятельным коммитом.
4. Периодически создаётся тег версии игры.

## 5. Что входит в школьный проект

Школьный форк сохраняет игровое ядро, но добавляет исследовательский контур:

```text
school-xai/
├── game/                  # постепенно выделяемые игровые адаптеры; не переписывать сразу
├── ml/
│   ├── features.py        # признаки игровой ситуации
│   ├── dataset.py         # сбор и подготовка обучающих примеров
│   ├── train.py           # обучение и сохранение модели
│   ├── policy.py          # единый интерфейс ML-политики
│   └── evaluate.py        # качество модели и сравнение с baseline
├── xai/
│   ├── model.py           # структуры наблюдений, действий и причин
│   ├── recorder.py        # журнал решений ИИ
│   ├── explanations.py    # перевод причин в объяснение для человека
│   └── overlays.py        # текстовые и пространственные подсказки
├── learning/
│   ├── lessons.py          # теория и интерактивные карточки
│   ├── questions.py        # вопросы на предсказание
│   ├── sandbox.py          # управляемая песочница
│   └── progress.py         # прогресс ученика
├── experiments/
│   ├── scenarios.py       # воспроизводимые сценарии
│   ├── runner.py          # запуск сценария с фиксированными условиями
│   ├── results.py         # ответы, время, оценки понятности
│   └── analysis.py        # расчёт метрик и экспорт таблиц/графиков
├── data/
│   ├── scenarios/         # описания сценариев
│   └── results/           # результаты экспериментов, без персональных данных
└── docs/
    ├── methodology.md     # методика исследования
    └── decisions.md       # принятые технические решения и ограничения
```

На первом этапе не нужно физически переносить все исходные файлы в папку `game/`. Это целевая структура. Безопаснее оставить рабочие модули на прежних местах, добавить новые независимые модули `ml/`, `xai/`, `learning/` и `experiments/`, а переносы выполнять только после появления тестов.

## 5.1. Что удаляется из школьного проекта

Школьный проект не является полной копией игры. Из baseline нужно оставить только механики, которые создают данные для ML-решений или помогают объяснить их пользователю.

| Компонент исходной игры | Решение в школьном проекте | Причина |
|---|---|---|
| Магазин и покупки | Удалить | Не создают признаков для ML и усложняют сценарии |
| Деньги, награды и прогресс | Удалить | Не нужны для исследования решений модели |
| Сохранения прохождения | Удалить или заменить учебным прогрессом | Мешают воспроизводимости сценариев |
| Достижения и задания кампании | Удалить | Не относятся к объяснимости модели |
| Полный инвентарь | Сократить до 2–4 источников сигналов | Нужны только предметы, влияющие на признаки |
| Редкие сюжетные и случайные события | Удалить из MVP | Усложняют контроль датасета |
| Полная атмосфера и декоративный HUD | Сократить | Не являются обязательными ML-данными |
| Свободное прохождение всех уровней | Заменить учебными сценами | Для эксперимента важнее управляемость |
| Полный редактор уровней | Не включать в первую версию | Достаточно фиксированной учебной карты |

### Что остаётся обязательным

- фиксированная карта с препятствиями и комнатами;
- перемещение игрока и призрака;
- поле зрения и проверка видимости;
- слух и источник звука;
- ограниченная навигация и маршрут;
- несколько действий игрока, создающих сигналы;
- пошаговое воспроизведение решений;
- визуализация признаков, предсказаний и объяснений.

Итоговая среда должна быть небольшой лабораторией: пользователь создаёт ситуацию, ML-модель принимает решение, а система показывает, какие признаки повлияли на результат.

## 5.2. Какие игровые механики демонстрируют ML

ML можно наблюдать не только при движении призрака. Механики следует разделить на источники признаков, объекты предсказания и визуальные последствия.

### Восприятие и классификация ситуации

Модель получает признаки игровой ситуации:

- игрок виден или скрыт;
- обнаружен звук или нет;
- игрок в той же комнате или в другой;
- расстояние до игрока и источника звука;
- есть ли доступный маршрут;
- сколько времени агент находится в текущем состоянии.

Результатом классификации может быть `PATROL`, `SEARCH`, `CHASE`, `RETURN` или `IDLE`.

### Звук и источники сигналов

Действия игрока могут создавать разные входные данные: перемещение, радио, громкий предмет, бросок или взаимодействие с объектом. Модель может предсказывать игнорирование сигнала, поиск источника или переключение на преследование.

Это позволяет показать конфликт признаков: звук есть, но игрок невидим; игрок видим, но звук отсутствует; доступны оба сигнала.

### Поле зрения и препятствия

Изменяя положение игрока и стен, можно показать:

- почему одинаковое расстояние не всегда даёт одинаковое решение;
- как препятствие меняет `player_visible`;
- какие признаки привели к обнаружению;
- почему визуальное объяснение должно опираться на реальные данные восприятия.

В пространственном режиме отображаются поле зрения, препятствие и позиция игрока. Это визуализация входных данных модели, а не выдуманная карта вероятностей.

### Предметы как генераторы признаков

Полный инвентарь не нужен. Можно оставить несколько предметов:

| Предмет или действие | Признак | Возможный результат |
|---|---|---|
| Радио или шумный предмет | `heard_sound`, `sound_distance` | `SEARCH` |
| Фонарик | `light_visible` или изменение видимости | обнаружение / `CHASE` |
| Соль или препятствие | `path_blocked`, `route_available` | другой маршрут / `RETURN` |
| Проектор или источник света | `area_signal_active` | изменение доступности зоны |

Если предмет не влияет на признаки или решение модели, его следует убрать из школьной версии.

### Потеря цели и контрфактические вопросы

Когда игрок исчезает из поля зрения или прекращает создавать звук, можно показать изменение признаков, предсказания и контрфактическое объяснение: «Если бы игрок остался видимым, модель выбрала бы `CHASE`».

### Пошаговое наблюдение

Игра должна уметь остановиться перед решением модели. Ученик видит признаки, делает прогноз, нажимает «Следующий шаг», а затем сравнивает свой ответ с предсказанием и объяснением модели.

## 5.3. Какие ML-темы освещаются

### Базовые темы машинного обучения

1. Признаки и целевая переменная: игровая ситуация → действие агента.
2. Обучающая выборка и разметка данных, полученная от FSM-baseline.
3. Классификация и различие обучения модели и инференса.
4. Разделение train/test и проверка на новых игровых ситуациях.
5. Метрики: accuracy, precision, recall, macro-F1 и матрица ошибок.
6. Дисбаланс классов, например слишком частый `PATROL`.
7. Переобучение на конкретную карту или координаты.
8. Утечка данных: запрет использовать будущие состояния и результаты действия.

### Темы explainable ML

1. Глобальное объяснение — какие признаки важны для модели в целом.
2. Локальное объяснение — почему в конкретной сцене выбран `SEARCH`.
3. Важность признаков и их фактические значения.
4. Уверенность модели и ситуации с близкими вероятностями классов.
5. Контрфактическое объяснение — что минимально изменить для другого действия.
6. Верность объяснения — соответствует ли оно реальному вычислению модели.
7. Понятность объяснения — помогает ли оно человеку предсказать действие.
8. Ограничения: важность признака не доказывает причинность.
9. Компромисс между качеством и интерпретируемостью модели.
10. Работа с ситуациями, отличающимися от обучающей выборки.

В первую версию не нужно включать глубокие нейросети, обучение с подкреплением, SHAP/LIME и обучение модели во время игры. Их можно оставить как направления развития после проверки базового эксперимента.

## 5.4. Дополнительные ML-механики

ML можно демонстрировать не только на выборе пути и состояния призрака. Дополнительные механики должны быть небольшими самостоятельными задачами, чтобы каждая имела понятные признаки, предсказание и объяснение.

| Механика | Что предсказывает модель | Как объясняется |
|---|---|---|
| Рекомендация предмета | Какой предмет использовать сейчас | «Выбран УФ-фонарь, потому что рядом обнаружены следы» |
| Успешность действия | Сработает ли спрятаться, убежать или применить предмет | Вероятности успеха и признаки, повлиявшие на прогноз |
| Классификация призрака | Тип призрака по собранным уликам | Улики подсвечиваются и ранжируются по вкладу |
| Оценка опасности комнаты | Низкий, средний или высокий риск | Показываются активность, расстояние, шум и видимость |
| Предсказание следующего события | Охота, нападение, исчезновение или патрулирование | Модель показывает классы событий и уверенность |
| Анализ улик | Какая улика сильнее поддерживает гипотезу | Сравнение влияния каждой улики на результат |
| Следующая рекомендация игроку | Какое действие выполнить дальше | «Спрячься: призрак близко и уже слышал звук» |

Эти механики не нужно реализовывать все сразу. Рекомендуемый состав первой расширенной версии: выбор действия призрака, рекомендация предмета и классификация типа призрака по уликам.

## 5.5. Темы ML и способы их наглядной демонстрации

| Тема | Как показать в интерфейсе | Что объясняет ученик |
|---|---|---|
| Признаки и целевая переменная | Карточки «видимость», «звук», «расстояние», «улики» → результат | Что модель получает на вход и что предсказывает |
| Обучающая выборка | Набор игровых ситуаций с правильными ответами | Как формируются данные для обучения |
| Разметка данных | FSM или учитель помечает действие/тип призрака | Откуда берутся целевые значения |
| Классификация | Модель выбирает действие, предмет или тип призрака | Как выбирается один класс из нескольких |
| Обучение и инференс | Отдельные кнопки «Обучить» и «Сделать прогноз» | Разницу между созданием модели и её применением |
| Train/test split | Обучение на одних сценах, проверка на новых | Почему нужно тестировать модель на новых данных |
| Дерево решений | Пошаговый путь по условиям до ответа | Как признаки привели к предсказанию |
| Важность признаков | Полосы или подсветка вклада признаков | Что сильнее всего повлияло на решение |
| Уверенность модели | Столбики вероятностей классов | Чем уверенный прогноз отличается от сомнительного |
| Ошибка модели | Предсказание рядом с правильным ответом | Почему ML может ошибаться |
| Матрица ошибок | Таблица «реальный класс → предсказанный класс» | Какие классы модель путает |
| Дисбаланс классов | Сравнение количества `PATROL`, `SEARCH`, `CHASE` | Почему частый класс может доминировать |
| Переобучение | Проверка на новой комнате или карте | Почему запоминание примеров не равно пониманию |
| Утечка данных | Наглядное сравнение разрешённых и запрещённых признаков | Почему нельзя использовать информацию из будущего |
| Контрфактическое объяснение | «Убери звук — модель выберет другое действие» | Что минимально изменить для другого результата |
| Сравнение моделей | Дерево и более сложная модель на одной сцене | Компромисс качества и объяснимости |
| Достоверность объяснения | Сравнение текста подсказки с реальным путём модели | Почему объяснение должно соответствовать вычислениям |
| Понятность объяснения | Вопрос ученику до и после показа объяснения | Помогает ли объяснение предсказывать модель |

## 6. Архитектура школьного проекта

### 6.1. Игровой слой

Игровой слой отвечает за фактическое состояние игры и не должен знать о том, как участнику показывается объяснение.

Основные точки интеграции:

- `main_work.Game.draw()` — последовательность обновления игровых систем;
- `ghost.Ghost.update()` — один шаг обновления призрака;
- `ghost.Ghost.update_state()` — вычисление перехода FSM;
- `ghost.Ghost.update_movement()` — выбор и выполнение движения;
- `ghost.GhostManager.update()` — обновление призраков и игровых взаимодействий;
- `draws.draw_game()` — отрисовка мира и HUD.

В школьной ветке сначала добавляется тонкий наблюдатель вокруг этих точек. Нельзя сразу переписывать `Ghost` или менять порядок вызовов в игровом цикле: baseline нужен для генерации данных и проверки ML-модели.

FSM-baseline выполняет две роли:

- создаёт размеченные примеры вида «ситуация → действие»;
- служит контрольной моделью для оценки качества ML-политики.

В экспериментальном режиме ML-политика должна действительно выбирать действие. Нельзя только добавить объяснение к старому FSM и называть это explainable ML.

### 6.2. Слой наблюдений и признаки ML

Наблюдение — это только те данные, которыми реально располагала модель в момент решения. Из наблюдения формируется фиксированный вектор признаков для обучения и инференса. Примеры признаков:

```text
player_visible, heard_sound, same_room, distance_to_player,
distance_to_sound, distance_to_home, state_timer,
current_state, target_available, aggression
```

Категориальные признаки кодируются одинаково при обучении и запуске игры. Нельзя передавать в модель информацию, которой не было доступно в реальном игровом моменте, например будущую траекторию игрока.

Минимальная структура события:

```python
DecisionEvent(
    timestamp_ms=12345,
    frame=740,
    ghost_id=0,
    state_before="PATROL",
    observations={
        "player_visible": False,
        "player_distance": 280.0,
        "heard_sound": True,
        "same_room": False,
        "target_available": True,
    },
    candidate_actions=["PATROL", "SEARCH", "CHASE"],
    action="SEARCH",
    reason_code="SOUND_DETECTED",
    state_after="SEARCH",
)
```

Поле `reason_code` должно быть машинно-читаемым и стабильным. Текст объяснения не следует записывать вместо причины: текст может меняться между режимами, а причина должна оставаться одной и той же.

Для обучения baseline генерирует `action` как метку. В дальнейшем ML-модель получает только `observations` и предсказывает `action` сама. `reason_code` используется для проверки и объяснения, но не должен подменять входные признаки.

Рекомендуемые причины для первой версии:

- `PLAYER_VISIBLE` — игрок доступен для преследования;
- `SOUND_DETECTED` — обнаружен источник звука;
- `PLAYER_LOST` — цель потеряна, начинается поиск;
- `SEARCH_TIMEOUT` — поиск завершён без нового сигнала;
- `PATROL_TIMER` — переход по таймеру патрулирования;
- `RETURN_HOME` — возврат в комнату или к исходной точке;
- `INVISIBLE_TIMER` — завершение периода невидимости.

Если конкретная причина пока не извлекается из текущего кода, её нельзя придумывать в интерфейсе. Сначала нужно добавить соответствующее наблюдение или пометить событие как `UNKNOWN`.

### 6.3. Журнал решений

`xai/recorder.py` должен:

- получать событие после фактического выбора действия;
- добавлять время, номер кадра и идентификатор сценария;
- поддерживать режимы `disabled`, `memory`, `jsonl`;
- не менять случайность, таймеры, скорость и порядок обновлений ИИ;
- ограничивать размер журнала в обычной игре;
- сохранять JSON Lines для последующего анализа.

Пример строки журнала:

```json
{"scenario_id":"sound_only_01","frame":740,"state_before":"PATROL","action":"SEARCH","reason_code":"SOUND_DETECTED","observations":{"heard_sound":true,"player_visible":false}}
```

Проверка корректности: запуск с отключённым журналом и с журналом при одинаковом seed должен дать одинаковую последовательность состояний, действий и координат призрака.

### 6.4. ML-модель и политика принятия решений

Для первой версии лучше использовать небольшую интерпретируемую модель классификации:

- `DecisionTreeClassifier` — наглядное дерево решений;
- `LogisticRegression` — понятное влияние признаков на классы действий;
- `RandomForestClassifier` — более устойчивое сравнение, но с менее простым объяснением.

Рекомендуемый первый вариант — дерево решений с ограниченной глубиной. Это настоящая ML-модель, которая быстро обучается на данных игры и позволяет показать ученику путь от признаков к решению. Позже можно сравнить её с Random Forest или небольшой нейросетью.

Интерфейс модели:

```python
action = policy.predict(observation)
explanation = policy.explain(observation, action)
```

`policy.py` возвращает единый результат: выбранное действие, вероятности классов, использованные признаки и версию модели. Артефакт модели хранится вместе с метаданными: версия датасета, seed, список признаков, классы и дата обучения.

Минимальный pipeline:

```text
FSM-baseline
    ↓ генерирует ситуации и метки
dataset.jsonl / dataset.csv
    ↓ train.py
ML-модель
    ↓ policy.py во время игры
решение + объяснение + журнал
```

Качество модели проверяется до подключения к игре: accuracy, macro-F1, матрица ошибок, доля неуверенных ситуаций и соответствие поведения baseline. При низкой уверенности должно отображаться состояние `LOW_CONFIDENCE` или использоваться явно описанное fallback-действие.

### 6.5. Слой объяснений ML

`xai/explanations.py` преобразует предсказание модели и фактические признаки в представление конкретного режима. Объяснение должно отвечать на два вопроса:

1. Почему модель выбрала это действие — важные признаки и их значения.
2. Что нужно изменить, чтобы модель выбрала другое действие — контрфактический пример.

Для первой версии достаточно показать путь по дереву решений, локальные важности признаков, вероятности классов и одно контрфактическое изменение. SHAP/LIME можно добавить позже, если базового объяснения будет недостаточно.

| Режим | Что включается |
|---|---|
| `none` | Ничего, только обычная игра |
| `text` | Короткое сообщение о признаках, предсказании и уверенности модели |
| `spatial` | Только реальные области зрения, слуха, цель и маршрут |
| `combined` | Текст плюс пространственные подсказки |

Слой объяснений не принимает собственных решений за призрака. Он только отображает уже зарегистрированное предсказание модели и его входные данные.

Важно различать факт и интерпретацию:

- факт: `heard_sound=True`;
- допустимое объяснение: «Призрак услышал звук и перешёл к поиску источника»;
- недопустимое без отдельной модели: «Призрак оценил вероятность нахождения игрока в этой точке как 82%».

### 6.6. Обучающий режим

Школьный проект должен содержать отдельный режим изучения:

```text
Обучение
├── Теория: признаки, обучение, классификация, XAI
├── Пошаговый урок: один игровой такт за раз
├── Предсказание: ученик выбирает действие ML-модели
├── Песочница: меняет признаки и запускает модель
└── Результат: правильность, уверенность и объяснение ошибки
```

Первая песочница должна быть управляемой: фиксированная карта и набор параметров `player_visible`, `heard_sound`, расстояния, состояние призрака и таймер. Полный редактор карт и свободное обучение модели не нужны для MVP.

Цикл задания:

1. Показать признаки ситуации, не раскрывая предсказание.
2. Попросить выбрать действие и назвать главный признак.
3. Запустить ML-инференс.
4. Показать действие, вероятности и объяснение.
5. Сравнить ответ ученика с моделью и эталонной разметкой.

Вопросы должны проверять именно прогноз поведения модели, например: «Если `heard_sound` изменить с `true` на `false`, изменится ли действие?».

### 6.7. Экспериментальный слой

Сценарий должен задавать:

- карту и уровень;
- начальные координаты игрока и призрака;
- состояние призрака до начала эпизода;
- доступные предметы и сигналы;
- seed случайности;
- длительность или условие завершения;
- правильный ответ о причине действия.

Минимальный набор сценариев:

1. Игрок виден — призрак выбирает `CHASE`.
2. Игрок не виден, но есть звук — призрак выбирает `SEARCH` или движение к источнику.
3. Цель потеряна — призрак остаётся в `SEARCH`, затем возвращается к патрулированию.
4. Одновременно доступны несколько сигналов — проверяется приоритет выбора.

Каждый сценарий должен запускаться повторно без ручного перемещения игрока. Для автоматического режима допустимо отдельное тестовое управление, которое создаёт сигналы напрямую, но оно не должно менять ML-модель. В результатах нужно фиксировать версию модели и датасета.

## 7. Порядок разработки школьной ветки

Разработка выполняется небольшими этапами:

### Этап 1. Baseline

- зафиксировать тег исходной игры;
- описать версии Python и зависимостей;
- сохранить видеозапись или скриншоты исходного поведения;
- добавить smoke-тест запуска и базовых переходов FSM.

### Этап 2. Наблюдаемость и датасет

- определить места выбора решения в `ghost.py`;
- ввести `DecisionEvent` и `reason_code`;
- добавить recorder в выключенном по умолчанию режиме;
- проверить совпадение поведения с baseline;
- добавить тест на заполнение журнала;
- собрать размеченный датасет ситуаций из FSM-baseline.

### Этап 3. Первая ML-модель

- выделить и документировать признаки;
- обучить дерево решений на датасете baseline;
- проверить accuracy, macro-F1 и матрицу ошибок;
- подключить `ml/policy.py` в отдельном экспериментальном режиме;
- убедиться, что игра использует предсказание ML-модели, а не старый FSM.

### Этап 4. Объяснение ML-модели

- добавить `xai/explanations.py`;
- показывать признаки, предсказание и уверенность;
- добавить важность признаков и простой контрфактический пример;
- проверить, что объяснение соответствует модели и журналу.

### Этап 5. Обучающий режим и пространственная визуализация

- отображать только фактическое поле зрения, радиус слуха, источник звука, цель и маршрут;
- согласовать координаты мира и камеры из `main_work.py`;
- добавить переключатель режимов;
- добавить теорию, вопросы на предсказание и управляемую песочницу;
- проверить, что overlay не влияет на коллизии и движение.

### Этап 6. Воспроизводимые эксперименты

- добавить сценарии, seed и runner;
- записывать режим, сценарий, ответ участника, время ответа и оценку понятности;
- исключить из результатов персональные данные;
- экспортировать CSV/JSON для анализа.

### Этап 7. Анализ и отчёт

- рассчитать точность, медианное время ответа и субъективную понятность;
- сравнить режимы `none`, `text`, `spatial`, `combined`;
- описать ограничения и случаи, когда объяснение было неполным;
- не формулировать вывод о пользе объяснений без данных участников или явно назвать результат автоматической проверкой.

## 8. Ветки внутри школьного проекта

```text
school-xai
 ├── ml/dataset-and-model
 ├── xai/telemetry
 ├── xai/ml-explanations
 ├── learning/theory-and-questions
 ├── learning/sandbox
 ├── xai/spatial-overlays
 ├── experiments/scenarios
 └── experiments/analysis
```

Рекомендуемый порядок слияния:

1. `xai/telemetry` — события и recorder.
2. `ml/dataset-and-model` — признаки, датасет и первая ML-модель.
3. `xai/ml-explanations` — объяснение предсказаний модели.
4. `learning/theory-and-questions` — теория и вопросы на предсказание.
5. `learning/sandbox` — управляемая песочница.
6. `xai/spatial-overlays` — пространственная визуализация.
7. `experiments/scenarios` — повторяемые сценарии.
8. `experiments/analysis` — результаты, метрики и графики.

Каждая ветка должна иметь проверяемый результат. Например, ветка telemetry не должна одновременно менять дизайн HUD, а ветка spatial-overlays не должна менять правила FSM.

## 9. Как переносить исправления из игры в школьный форк

После форка игра и исследование могут развиваться параллельно. Если исправление игры необходимо в школьном проекте:

1. проверить, не меняет ли оно поведение, которое измеряется в эксперименте;
2. перенести только конкретный коммит через `git cherry-pick` или вручную;
3. повторно запустить baseline-сценарии;
4. зафиксировать новую версию игрового ядра в `docs/decisions.md`.

Не следует регулярно вливать весь `main` в школьную ветку без проверки: это может незаметно изменить условия эксперимента, интерфейс или результаты.

## 10. Критерии готовности

### Готовность игры

- чистый клон запускается по инструкции README;
- основной игровой сценарий проходит от старта до завершения;
- сохранения и уровни не зависят от файлов разработчика;
- версия зафиксирована тегом.

### Готовность школьного проекта

- есть обученный ML-классификатор, а не только правила FSM;
- зафиксированы признаки, датасет, seed и версия модели;
- ML-модель действительно выбирает действия в отдельном режиме игры;
- качество модели сравнено с FSM-baseline;
- журнал содержит фактические решения и наблюдения;
- запись журнала не меняет поведение ИИ;
- объяснение показывает признаки, уверенность и ограничения модели;
- для одного сценария доступны все четыре режима сравнения;
- доступны теория, вопросы на предсказание и управляемая песочница;
- сценарии повторяемы при фиксированном seed;
- spatial overlay не показывает несуществующие данные;
- ответы и время участников сохраняются в обезличенном формате;
- есть автоматические проверки корректности причин;
- отчёт отделяет измеренные результаты от предположений.

## 11. Риски и решения

| Риск | Решение |
|---|---|
| Логирование меняет тайминги и поведение | Лёгкий recorder, режим `disabled`, тест сравнения trajectory/state |
| Модель только имитирует FSM и не проверяется отдельно | Хранить baseline как учителя, измерять качество на отложенной выборке и явно включать ML-policy в эксперименте |
| Модель использует недоступный в момент решения признак | Зафиксировать feature contract и проверять состав входного вектора тестом |
| Объяснение выглядит убедительно, но не соответствует модели | Генерировать его из фактического дерева/вклада признаков, а не из заранее написанных причин |
| Причина решения не видна в одном месте кода | Сначала добавить события на границах `update_state()` и `update_movement()`, затем уточнять контекст |
| Overlay рисует данные, которых нет у ИИ | Разрешить только поля из `DecisionEvent` и проверять их тестом |
| Перенос изменений из игры ломает эксперимент | Переносить точечные коммиты и повторять baseline-сценарии |
| Смешиваются игровая и научная цели | Разные ветки, разные README и разные критерии готовности |
| Нельзя доказать понятность людям | Не выдавать автоматическую корректность за пользовательское исследование |
| Проблемы лицензии при публикации форка | Проверить лицензию, авторство и обязательные уведомления до публикации |

## 12. Рекомендуемое решение для этого репозитория

1. Оставить текущий `main` проектом игры.
2. Добавить документацию и довести игру до проверяемого baseline.
3. Создать тег `game-v1.0-baseline`.
4. От этой точки создать `school-xai` и развивать школьную часть отдельно.
5. На первом этапе школьского проекта не делать большой перенос файлов: добавить небольшие модули `ml/`, `xai/`, `learning/` и `experiments/` рядом с существующим кодом.
6. Обучить первую интерпретируемую ML-модель на данных FSM-baseline и подключить её отдельным режимом.
7. После появления тестов при необходимости выделить игровые адаптеры и общие структуры.
8. Публиковать школьный проект как отдельный репозиторий только после проверки лицензии и удаления локальных сохранений.

Такое разделение сохраняет игру пригодной для обычной разработки и одновременно даёт школьному проекту стабильную, воспроизводимую основу для исследования XAI.
