# Development Plan: Retro Ghost Hunt Production

Документ фиксирует план развития игры до красивой, цельной и релизной ретро-игры про поиск призраков. Текущая база уже играбельна: есть Pygame-цикл, меню, магазин, инвентарь, журнал улик, 2 уровня, сохранения, прогрессия, ИИ призрака, предметы расследования и редактор уровней. Дальше цель не просто "добавить еще", а собрать игру в узнаваемый продукт с сильным визуальным стилем, понятной петлей расследования, атмосферой, балансом и подготовкой к мобильным платформам.

---

## 0. Продуктовое Видение

**Жанр:** 2D top-down ретро-хоррор/детектив с поиском призраков.

**Целевая эмоция:** игрок входит в странное место, собирает улики, ставит оборудование, слышит и видит тревожные сигналы, делает вывод в журнале и уходит до того, как призрак его догонит.

**Ключевой принцип:** игра должна выглядеть как цельная ретро-игра, а не как набор тестовых ассетов. Каждый экран, фон, предмет, UI и звук должны поддерживать одну атмосферу.

**Референс-направление без копирования:** пиксельный хоррор, VHS/CRT, старая доска расследования, пыльные дома, школьные коридоры, заброшенные кабинеты, слабый фонарик, редкие вспышки улик.

## 5. Геймплейная Петля Расследования

### 5.1 Цикл Одного Уровня

1. Игрок выбирает снаряжение в магазине.
2. Заходит на уровень и ищет активную комнату/зону.
3. Ставит оборудование и проверяет улики.
4. Призрак становится активнее, растет риск охоты.
5. Игрок отмечает улики в журнале.
6. Игрок выбирает тип призрака и подтверждает вывод у компьютера/выхода.
7. Игра показывает отчет, награду и открывает следующий уровень.

### 5.2 Улики

- [ ] ЭМП должен давать уровни 1-5, где 5 является уликой.
- [ ] УФ должен проявлять следы, отпечатки, символы или надписи.
- [ ] Радио должно иметь короткие ответы, зависящие от типа призрака и расстояния.
- [ ] Проектор должен показывать силуэт/сферу/искажение только в зоне активности.
- [ ] Соль и красная пыль должны фиксировать маршрут призрака и влиять на поведение.
- [ ] `ghostorb` из `ghost_abilities.ini` нужно довести до видимой механики.

### 5.3 Риск и Напряжение

- [ ] Ввести шкалу тревоги/активности призрака вместо невидимого "страшно".
- [ ] Добавить фазы: спокойствие, активность, предупреждение, охота, затишье.
- [ ] Во время охоты часть предметов работает хуже или с задержкой.
- [ ] Дать игроку способы защиты: спрятаться, выключить фонарь, использовать крест, закрыть дверь.
- [ ] Сделать повреждение/поражение честным: игрок должен понимать, почему умер.

## 7. Мобильные Платформы

### 7.1 Решение По Технологии

Текущий проект на Pygame можно попробовать перенести на Android через `pygame-ce` + `buildozer`/`python-for-android`, но это рискованный путь для продакшена. Для серьезного мобильного релиза нужно сравнить два варианта.

**Вариант A: оставить Pygame и портировать.**

- Плюсы: меньше переписывания, быстрее прототип Android.
- Минусы: сложнее с iOS, сборками, производительностью, сенсорным UI, магазинными требованиями.

**Вариант B: перенос на Godot.**

- Плюсы: нормальный экспорт Android/iOS/Windows, сцены, тайлы, звук, UI, touch controls.
- Минусы: нужно перенести логику, уровни и ассеты.

**Рекомендация:** сначала довести PC-версию до vertical slice, затем сделать технический spike на Android. Если порт Pygame не дает стабильные FPS/сборку за 1-2 недели, переносить на Godot.

### 7.2 Mobile Readiness Внутри Текущего Кода

- [ ] Отвязать игру от фиксированных `SCREEN_WIDTH = 1024`, `SCREEN_HEIGHT = 768`.
- [ ] Ввести виртуальное игровое разрешение и масштабирование под разные экраны.
- [ ] Вынести ввод в слой `InputController`: клавиатура, мышь, touch.
- [ ] Сделать экранные кнопки: движение, предметы, журнал, взаимодействие, бег/скрытность.
- [ ] Увеличить размеры кликабельных зон UI.
- [ ] Проверить читаемость журнала на 16:9, 19.5:9 и планшетах.
- [ ] Сделать настройку качества: CRT on/off, частицы on/off, лимит FPS.

### 7.3 Мобильный UX

- [ ] Правая зона: использовать предмет, сменить предмет, журнал, взаимодействие.

Цель: короткая, но цельная кампания.

Цель: игра не ломается у игроков.

### Milestone 5: Mobile Spike

Цель: принять техническое решение по мобильным платформам.

**Критерий готовности:** есть рабочий APK-прототип или аргументированное решение переносить движок.

- [ ] Все ассеты лежат в понятной структуре и не имеют временных имен.
- [ ] Нет битых путей к файлам при запуске из другой директории.
- [ ] Нет пользовательских экранов с debug-текстом.
- [ ] Есть настройки звука, экрана и управления.
- [ ] Есть туториал или первый уровень, который обучает без длинного текста.
- [ ] Есть QA-чеклист перед релизом.
- [ ] Есть трейлерный фрагмент: 30-45 секунд красивого, понятного геймплея.

---

## 12. Важное Решение

Самый большой выигрыш сейчас даст не добавление десятков новых механик, а сборка одного идеального уровня. Если первый уровень станет красивым, атмосферным и понятным, остальные уровни можно масштабировать по шаблону. Если продолжать добавлять контент поверх смешанного визуала, игра будет расти, но ощущение "скучно и уродливо" останется.

Поэтому ближайший фокус: **Visual Vertical Slice уровня 1 + сильная петля расследования + новый HUD/журнал + звук.**
